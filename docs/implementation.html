Why I built this

  • I knew caching, rate limiting and auth in theory. I wanted to build them into a small API and see what actually happens when requests come in.
  • Products were just a simple resource to work with. The other goal was learning Locust basics: generating load, comparing cache ON and OFF, and not trusting a single fast request.

Read Redis before PostgreSQL

Caching
  • I cache GET /api/products/ under products:list:v1.
  • On a hit I return the cached list. On a miss I read PostgreSQL and store a JSON copy with a configurable TTL.
  • Pydantic turns the JSON back into response models. An empty list still counts as a hit.

Not covered yet: the single-product endpoint isn't cached, and there's no pagination or protection against many cache misses at once.

product_cache.py

Clear the list after a write

Caching
  • After a successful create, update or delete, the service deletes the list key.
  • The next list request reads fresh data from PostgreSQL and fills the cache again.
  • I only invalidate after the database call succeeds, so a failed update doesn't look like a change.

Tradeoff: if deleting the key fails after a commit, I still return success and log it. Old data can stay until the TTL runs out.

product_service.py

Fixed-window rate limiting

Traffic
  • I count requests per client IP and endpoint in Redis. The first request starts the window.
  • A Lua script increments the counter and sets the expiry in one atomic step.
  • Going over the limit returns 429 with Retry-After. Login and register allow 5 attempts per 60 s per IP.

This isn't a token bucket. The counter resets at the end of the window, so bursts around the boundary are possible, and users behind the same IP share a limit.

limiter.py

When Redis goes down

Traffic
  • Cache errors and timeouts fall back to PostgreSQL. Failed cache writes get logged.
  • The product-list limiter is fail-open: reads keep working without rate limiting.
  • Login and register are fail-closed: they return 503 if the limiter is unavailable.

I'd rather keep product reads up than allow unlimited login attempts. The cost is more load on PostgreSQL while Redis is down.

dependencies.py

Password handling

Auth
  • Passwords are stored as Argon2 hashes via pwdlib, never as plain text.
  • If the email doesn't exist, I still verify against a dummy hash so the response doesn't come back instantly.
  • Wrong password, missing account and inactive user all get the same error. Hashing runs in a thread pool so it doesn't block the event loop.

The dummy hash removes one timing difference; it doesn't make the whole request constant-time. Registration still says when an email is taken.

auth_service.py

JWT and admin checks

Auth
  • Login issues a signed token with a user ID and expiry. I check the signature and required claims.
  • /api/users/me loads the current active user. Product writes also need is_admin=true.
  • Registration can't set the admin flag, and permissions are read from the database, so removing admin takes effect on the next request.

Left out on purpose: refresh tokens and instant token revocation. JWT payloads are readable, not encrypted.

dependencies.py

Layered database access

Database
  • Routers handle HTTP, services do the work, repositories talk to PostgreSQL with async SQLAlchemy.
  • Alembic tracks schema changes. A unique constraint protects email registration, even with parallel requests.
  • Repository errors roll back the session, and password hashes never appear in user responses.

Tests and CI

pytest
  • I test CRUD, cache hits and misses, Redis errors, JWT validation and admin permissions.
  • Repository tests use a separate PostgreSQL database. Redis is mocked, so these aren't real Redis integration tests.
  • GitHub Actions spins up PostgreSQL and runs pytest on every push and pull request.
Workflow runs

Load testing with Locust

Locust
  • I compared cache ON and OFF with 2 and 500 products, three runs per mode.
  • The benchmark page shows response times, percentiles, throughput and every single run.
  • Everything shared one laptop, and I didn't measure SQL query counts, so this isn't a production capacity number.

These runs were recorded before the later auth and logging changes.

How I measured

Docker and logging

Docker
  • Compose starts FastAPI, PostgreSQL and Redis. The API waits for healthy databases and runs migrations first.
  • PostgreSQL data lives in a named volume, and secrets are passed at runtime, not baked into the image.
  • Request logs show method, path, status and duration. Cache logs show HIT, MISS and ERROR.

The health check only hits the OpenAPI document, so it tells me the API responds, not that the databases are still reachable.

Current limits

  • I kept the API small on purpose so I could focus on these pieces. It runs locally; this page doesn't call a live API.
  • Before a real deployment it would need pagination, refresh tokens, proxy-aware client IPs and stronger cache consistency.
